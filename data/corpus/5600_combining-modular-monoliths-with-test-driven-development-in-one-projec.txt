Combining Modular Monoliths with Test-Driven Development in One Project

Real projects rarely use one idea in isolation. This article shows how Modular Monoliths and Test-Driven Development can work together in a single project.

Modular Monoliths is single deployable applications built from well-separated internal modules. Test-Driven Development is a workflow where you write a failing test first and then write code to make it pass.

Imagine a project that involves small teams and designing small modules. Modular Monoliths brings module boundaries, while Test-Driven Development brings red, green, refactor.

A sensible plan is to start with ArchUnit for the Modular Monoliths part and pytest for the Test-Driven Development part, and to keep the two sides connected through a small, well-tested interface.

Be prepared for combined risks: no enforced boundaries on one side, and skipping the refactor step on the other.

Picture the whole as an apartment building with separate flats under one roof, working alongside writing the exam questions before teaching the lesson.

Two habits help: first, enforce boundaries with automated checks; second, keep each red-green cycle to a few minutes.
