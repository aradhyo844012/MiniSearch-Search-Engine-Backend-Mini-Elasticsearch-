Combining Raft Consensus with Event Sourcing in One Project

Real projects rarely use one idea in isolation. This article shows how Raft Consensus and Event Sourcing can work together in a single project.

Raft Consensus is an algorithm that lets a group of servers agree on a shared log of operations. Event Sourcing is a design in which every change is stored as an immutable event and state is rebuilt from them.

Imagine a project that involves configuration stores and audit trails. Raft Consensus brings leader election, while Event Sourcing brings event log.

A sensible plan is to start with etcd for the Raft Consensus part and Apache Kafka for the Event Sourcing part, and to keep the two sides connected through a small, well-tested interface.

Be prepared for combined risks: slow disks causing elections on one side, and unbounded replay times on the other.

Picture the whole as a committee that elects a chair and only records decisions most members confirm, working alongside a bank statement that lists every transaction instead of only the balance.

Two habits help: first, use an odd number of nodes; second, version your events from the first day.
