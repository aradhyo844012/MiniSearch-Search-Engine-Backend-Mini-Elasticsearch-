Combining Raft Consensus with Idempotency in One Project

Real projects rarely use one idea in isolation. This article shows how Raft Consensus and Idempotency can work together in a single project.

Raft Consensus is an algorithm that lets a group of servers agree on a shared log of operations. Idempotency is the property that repeating an operation gives the same result as doing it once.

Imagine a project that involves configuration stores and payment APIs. Raft Consensus brings leader election, while Idempotency brings idempotency keys.

A sensible plan is to start with etcd for the Raft Consensus part and Stripe idempotency keys for the Idempotency part, and to keep the two sides connected through a small, well-tested interface.

Be prepared for combined risks: slow disks causing elections on one side, and side effects outside the guarded step on the other.

Picture the whole as a committee that elects a chair and only records decisions most members confirm, working alongside pressing an elevator call button many times and still getting one elevator.

Two habits help: first, use an odd number of nodes; second, store the result with the key so retries return the same response.
